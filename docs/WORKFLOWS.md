# Подключение, регрессия и проверка оценщика

Команды ниже используют собранный CLI: `npm run build`. После `npm link` вместо `node dist/cli.js` можно писать `agent-lab`.

## Подключение на текущей машине и в CI

```sh
node dist/cli.js doctor --connection examples/connection.json --yes --output doctor.json
node dist/cli.js suites --directory .evals
node dist/cli.js evaluate --input .evals/regression.json --connection connection.json --yes
```

`connection.json` имеет формат `agent-lab-connection-1`, поля `target`, необязательные `targetVersion` и `probe`. Пути модуля, рабочей папки и промпта разрешаются относительно файла. Относительная команда разрешается относительно `cwd`, её аргументы остаются отдельными аргументами. Значения HTTP-заголовков по-прежнему берутся из названных переменных окружения, не из сохранённых секретов.

Успешный внешний прогон или doctor сохраняет `.agent-lab/connection.local.json`. Следующая подготовка без явного `target` использует его и показывает подключение перед запуском. Явный target или connection имеет приоритет. `evaluate` использует подключение набора, пока не передан `--connection`; override применяется **до проверки путей**. Кэш текущей машины не подменяет подключение CI. Старый probe сохраняется при повторном использовании того же target.

Doctor выполняет ровно три запроса: `write.message`, затем `read.message` в той же сессии, затем `reset.message` в новой. Сверяет точные ожидаемые ответы, проверки после второго хода и исходные записи после сброса. Ожидания read/reset обязаны различаться. Также нужны `resetConfirmed`, `eventsComplete` и стабильная `version`. Это проверка поведения, заданного владельцем адаптера. Отчёт включает исходные трассы, а не только зелёный индикатор.

Рабочий пример — [connection.json](../examples/connection.json) и [stateful-agent.py](../examples/stateful-agent.py). Адаптер использует отдельный файл SQLite на каждый диалог, транзакцию изменения и чтение итогового состояния из БД. Это детерминированный пример, не модельный агент. Для AIGW есть [aigw-observed.py](../examples/aigw-observed.py): он проверяет отсутствие прежней беседы в PostgreSQL, читает её состояние и связывает события IDP/SBE с конкретным запросом. Он не сбрасывает бизнес-системы. Запускайте его Python из `.venv` AIGW, передав путь проекта единственным аргументом.

## Контракт наблюдения

Для настоящей модели есть [llm-stateful-agent.mjs](../examples/llm-stateful-agent.mjs), [промпт](../examples/llm-prompt.md) и [подключение](../examples/llm-connection.json):

```sh
node dist/cli.js doctor --connection examples/llm-connection.json --yes
```

Используются настроенные в Pi ключи; модель по умолчанию — OpenRouter / Claude Haiku 4.5. `AGENT_LAB_PROVIDER` и `AGENT_LAB_MODEL` выбирают модель испытуемого независимо от судьи. У каждого диалога своя SQLite-база и сессия SDK. Инструмент читает БД и завершает транзакцию до возврата результата модели; snapshot повторно читается из БД. Адаптер возвращает хеш кода и выбранную модель в идентичности версии, хеш применённого промпта, полные события зарегистрированных инструментов и наблюдённый расход SDK. Ограничения: до 12 модельных запросов на ответ и 48 на сессию. Доступ к провайдеру нужен; подмены ответов детерминированным демо нет. Это отдельный учебный агент, а не расширение API AIGW.

Дополнительные поля ответа адаптера:

| Поле | Смысл |
|---|---|
| `records` | Итоговый снимок, прочитанный адаптером. Заменяет предыдущий снимок целиком. |
| `resetConfirmed` | Первая реплика подтверждает применение исходного состояния/создание чистой сессии. |
| `eventsComplete` | В ответ включены все события инструментов за этот ход. |
| `eventScope` | Необязательный список инструментов, для которых заявлена полнота. Поддерживает префикс с `*` в конце, например `sbe_*`. Без поля заявление относится ко всем инструментам. |
| `sessionId`, `turn` | Если переданы, должны соответствовать текущей сессии и номеру хода, начиная с 1. |
| `version` | Идентификатор фактически запущенного удалённого релиза. Смена внутри прогона останавливает измерение. |
| `usage` | Расход за этот ответ: `calls`, `inputTokens`, `outputTokens`, `costUsd`. Не накопительный счётчик. Неизвестная цена — `null`; если данных нет, поле опускается. |
| `promptHash` | Подтверждение применения переданного промпта, если задан `target.promptFile`. |

Без последнего снимка, необходимого поля или подтверждения сброса проверка состояния получает `invalid`. Без полной трассы нельзя утверждать отсутствие действия или считать вызовы; проверки за пределами `eventScope` тоже не измерены. Метаданные сообщает адаптер: лаборатория не превращает их в независимое доказательство доверенности внешней системы. Старые текстовые адаптеры продолжают работать для текстовых проверок.

Стоимость внешнего агента показывается отдельно от модели лаборатории. Если хотя бы один ход не сообщил расход, итоговая цена внешнего диалога неизвестна. Расходы внешнего разговора с Pi не измеряются.

## Ожидания и исходные данные

На доске: карточка → `e` → «Критерий успеха». Можно редактировать конкретную проверку или рубрику и добавить текстовое сравнение, поле состояния либо условие вызова инструмента без JSON. Остальные критерии сохраняются. «Проверить ожидание на примерах» проверяет хороший и плохой ответы текстовыми предикатами и, после подтверждения, настоящим судьёй по агентским рубрикам. Состояние и действия без трассы остаются неизмеренными.

В разговоре доступен `agent_lab_preview`, в CLI:

```sh
node dist/cli.js preview --id RUN --scenario CASE --input examples.json --yes
# examples.json: {"good":"Which record?", "bad":"I don't have a record. Which record?"}
# --code-only вместо --yes: только текстовые предикаты, без модели
```

Предпросмотр сохраняет отдельный JSON в `.agent-lab/previews/`: оба примера, критерии, источники, версию судьи, оценки с доказательствами, исходные ответы и расход. По два независимых вызова на рубрику и пример в пределах сохранённых лимитов. Неверные ссылки и недословные цитаты отклоняются; исправления ответов судьи отключены. Примеры не превращаются в запуски агента или человеческие вердикты. Exit codes: 0 — оба результата соответствуют примерам, 1 — есть расхождение, 2 — оценка неполна.

В карточке и HTML видна связь с требованием и точной цитатой источника. Ответы на блокирующие вопросы добавляются отдельным материалом, прежний черновик сохраняется:

```sh
node dist/cli.js clarify --id RUN --input answers.json
# answers.json: [{"question":"Точный вопрос из черновика", "answer":"Ответ владельца"}]
```

Локальный импорт принимает JSON-массив или JSONL с одним объектом в строке:

```sh
node dist/cli.js build --input task.json --golden-file golden.json
node dist/cli.js build --input task.json --dialogues-file conversations.jsonl
```

Форматы объектов описаны в [справочнике](REFERENCE.md). В Pi те же файлы передаются как `goldenFile` и `dialoguesFile` инструменту `agent_lab_build`. Передавайте подходящую для обработки выборку: импорт валидирует структуру, но не обещает автоматического обезличивания. Генерация всегда получает `synthetic`; curated/production назначаются только соответствующими путями импорта. Правка общего профиля показывает число связанных карточек, а исходные данные остаются сохранёнными.

## Переоценка уже записанных ответов

```sh
node dist/cli.js reassess --id RUN --input criteria.json --yes
node dist/cli.js reassess --id RUN --code-only
# --trial TRIAL_ID можно повторять
```

```json
{
  "criteria": [{
    "scenarioId": "case_1",
    "checks": [{"id":"answer", "kind":"answer_equals", "description":"Точный ответ", "value":"Готово"}]
  }],
  "judge": {"provider":"YOUR_PROVIDER", "model":"YOUR_MODEL"}
}
```

Разрешено менять только checks, metrics и successCriteria. Неуказанные критерии сохраняются. Новый результат содержит `assessmentOf`, идентификаторы исходных диалогов, хеш фактов и версию оценщика; исходная запись не меняется. Агент и симулятор не вызываются. Проверяются полнота рубрик и существование цитируемых событий. HTML показывает старые и новые оценки рядом. Это не считается исправлением агента. `--code-only` не вызывает модель; оставшиеся рубрики помечаются как не переоценённые.

В `settings.roles` можно отдельно указать `builder`, `simulator`, `judge`, каждый с provider/model. Для builder/simulator незаполненная роль использует общую модель. Судья выбирается в порядке `roles.judge → settings.judge → общая модель`. `settings.judge` дополнительно принимает `upstream` для OpenRouter. Явный `judge` в запросе переоценки заменяет прежний выбор и сохраняет маршрут. Правка одной роли сохраняет остальные; `patch.settings.roles.judge: null` сбрасывает override судьи. На доске это «Настройки → Модели ролей». Версии критериев, инструкций оценщика и моделей отображаются в отчёте; сравнение несовместимых условий не объявляет улучшение. Устройство и ограничения: [EVALS-METHOD.md](EVALS-METHOD.md).

Отчёт переоценки сравнивает согласие старого и нового судьи с исходными человеческими метками. Используются только совпадающие трассы и неизменные критерии; метка по изменённой рубрике не переносится автоматически. Метки остаются ссылками на исходный разбор. Для сравнения двух версий агента новым судьёй переоцените оба исходных прогона: если сохранена связь повторного запуска с исходным, критерии и оценщик совпадают, `diff` сравнит эту пару. Одиночная переоценка не доказывает исправление агента.

## Один промпт, просмотр diff, повтор всего набора

Адаптер должен принимать `prompt` из запроса и возвращать `promptHash = SHA256(JSON.stringify(prompt))` в каждом ответе. Модуль получает оба поля в `createSession`; HTTP и command — в запросе. В `target.promptFile` укажите единственный разрешённый текстовый файл. Пример SQLite поддерживает этот контракт, AIGW HTTP API его не поддерживает и явно отклоняет подмену.

После ручного разбора ошибки:

```sh
node dist/cli.js prompt-propose --id RUN --candidate candidate.md \
  --hypothesis 'Использовать последнее уточнение' --trial FAILED_TRIAL
node dist/cli.js prompt-apply --input .agent-lab/prompt-proposals/ID/proposal.json --yes
node dist/cli.js run --id NEW_DRAFT --yes
node dist/cli.js diff --before RUN --after NEW_DRAFT
```

В Pi `agent_lab_prompt` готовит diff из текста кандидата; apply просит просмотреть именно эту версию, затем `agent_lab_run` показывает план тестов. Предложение должно ссылаться на реальные человеческие вердикты по ошибкам агента в dev. Ошибки симулятора, невалидные тесты и control не используются. Дрейф исходного файла, кандидата или просмотренного предложения блокирует применение.

Apply выбирает отдельный `candidate.md` для тестового запуска. Исходный файл не меняется. Все capability/regression-карточки, режимы и повторы сохраняются. Проверка кандидата не развёртывает его в сервисе. Legacy sandbox-улучшатор также учитывает агентские рубрики; неполная оценка блокирует принятие кандидата.

## CI и проверка пользы режимов

```sh
node dist/cli.js evaluate --input examples/regression-suite.json --connection examples/connection.json --yes
node dist/cli.js pilot --id RUN
```

Первую команду можно выполнить без ключей модели. [regression-ci.yml](../examples/regression-ci.yml) — готовый пример для `.github/workflows/`: проверяет набор и сохраняет артефакты даже при ошибке. Сохранённый suite включает представительный исходный trial на карточку и относящиеся к нему человеческие заметки. Они не становятся оценками нового запуска. Если исходных трасс нет, отчёт сообщает об этом.

`pilot` и HTML отдельно показывают подтверждённые человеком группы провалов, дополнительные находки режима на сопоставимых попытках, ошибки симулятора, расходы и время разбора. Засекается время открытого диалога и формы вердикта, включая простой; чтение в других приложениях не измеряется. Ошибки реактивного симулятора учитываются только там, где он действительно вызывался. Группа — family + критерий, а не доказанная независимая причина. Без человеческих решений дополнительная польза реактивного режима не объявляется установленной.

Основной [.github/workflows/check.yml](../.github/workflows/check.yml) теперь тоже запускает сохранённый SQLite-набор и загружает доказательства через `upload-artifact`, включая упавший прогон.

Пример workflow использует интерфейсы из официальных README [checkout](https://github.com/actions/checkout), [setup-node](https://github.com/actions/setup-node), [setup-python](https://github.com/actions/setup-python) и [upload-artifact](https://github.com/actions/upload-artifact), проверенные 2026-09-13. Команда набора проверена локально; workflow на GitHub в этой работе не запускался.
