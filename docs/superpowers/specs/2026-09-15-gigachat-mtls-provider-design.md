# GigaChat через mTLS как провайдер Agent Lab

## Цель

Перенести весь текущий функционал Agent Lab на возможность выбора GigaChat как
модели — с полной поддержкой функциональности, наравне с внешними провайдерами.
То есть при `provider: 'gigachat'` должны работать все три роли, которые сегодня
используют модель: симулятор пользователя, судья со строгим структурированным
выводом и sandbox-агент с реальными tool calls.

Сейчас `settings.provider`/`settings.model` — просто строка, которую
`createPiRuntime()` передаёт в `ModelRuntime.getModel()` из Pi SDK. Сам
репозиторий не регистрирует ни одного провайдера: доступные провайдеры приходят
из конфигурации Pi вне проекта. Внутренний GigaChat за mTLS туда не вписывается,
потому что декларативный `models.json` не умеет клиентские сертификаты.

## Подтверждено живым прогоном

Диагностический скрипт `test/live/probe-gigachat-mtls.ts` (ветка
`probe/gigachat-mtls-contract`) прогнан с боевыми сертификатами против
внутреннего контура. Результаты:

- Аутентификация — **только клиентский сертификат**, без обмена на OAuth-токен.
  Заголовка `Authorization` нет вовсе.
- Хост отвечает **на обоих контрактах**:
  - `POST {base}/v1/chat/completions` → legacy-ответ с `choices[0].message.content`,
    `usage.prompt_tokens/completion_tokens/total_tokens`;
  - `POST {base}/v2/chat/completions` → primary-ответ с
    `messages[].content[].text`, `usage.input_tokens/output_tokens/total_tokens`
    и `input_tokens_details.cached_tokens`.
- Префикс `/api/` внутренним шлюзом **не используется** (даёт 404), в отличие от
  публичного API.
- Модель `GigaChat-2-Max` отвечает (возвращает себя как `GigaChat-2-Max:2.0.28.2`).
- CA-цепочки на руках нет; прогон выполнен с отключённой проверкой серверного
  сертификата.

## Выбор контракта: v2

Целевой контракт — **primary v2**. Причины:

- Это текущая основная поверхность API; legacy-контракт в официальном SDK уже
  описан как compatibility shim (`MIGRATION_GUIDE.md` в `ai-forever/gigachat`).
- Только в v2 tool calling специфицирован явно и целостно (`tools`,
  `tool_config`, `function_call`/`function_result`, `tools_state_id`).
  В legacy-контракте это узкий и устаревший `functions`/`function_call`.
- Только в v2 структурированный вывод — часть контракта
  (`model_options.response_format`, включая `json_schema` и `regex`), что нужно
  судье.
- Оба контракта доступны на одном хосте, так что выбор v2 ничего не ломает и не
  требует отдельного URL.

Поэтому соседний `agent_oc` здесь не образец: он запинен на SDK 0.1.43, который
появился до v2, и потому ходит в `/v1/`.

## Архитектура

Нативный провайдер Pi SDK (`Provider` из `@earendil-works/pi-ai`),
регистрируемый программно на `modelRuntime` внутри `createPiRuntime()` — не через
`~/.pi/agent/models.json` и не через отдельный процесс-шлюз. Для остального кода
`provider: 'gigachat'` неотличим от любого другого провайдера.

## Компоненты

### `src/giga-provider.ts` (новый файл)

Экспортирует `createGigaChatProvider(env = process.env): Provider | undefined`.

- Конфигурация из переменных окружения:
  `GIGACHAT_URL`, `GIGACHAT_CERT_PATH`, `GIGACHAT_KEY_PATH` — обязательные;
  `GIGACHAT_CA_PATH`, `GIGACHAT_INSECURE` — опциональные (см. «Проверка TLS»).
  Без обязательных переменных функция возвращает `undefined`, провайдер просто
  не регистрируется.
- Запрос: `POST {GIGACHAT_URL без хвостового /v1|/v2}/v2/chat/completions`,
  клиентский сертификат на каждом запросе, без `Authorization`.
- Статический список моделей: `GigaChat-2-Max`, `GigaChat-2-Pro`. Простой массив,
  расширяется по мере надобности.

### `src/pi.ts` (правка)

В `createPiRuntime()`, сразу после создания `modelRuntime` (только на ветке
реального создания, не на `injectedRuntime`), вызывается
`createGigaChatProvider()`, и если она вернула провайдера —
`modelRuntime.registerProvider('gigachat', ...)`.

## Маппинги (ядро работы)

Это то, что определяет «полную работоспособность»; каждый пункт проверен по
исходникам pi-ai и по записям реальных вызовов GigaChat.

### Сообщения

pi-ai `Context.messages` (роли + текст) → v2
`messages: [{role, content: [{text}]}]`. Контент в v2 — всегда список частей,
даже для простого текста. Обратно: текст ответа собирается как конкатенация
`text` всех частей ассистентского сообщения.

### Структурированный вывод судьи

`src/pi.ts` добавляет строгую схему через хук `onPayload`, подсовывая
**OpenAI-форму** `response_format: {type: 'json_schema', json_schema: {name,
strict, schema}}` (см. `JUDGE_RESPONSE_FORMAT` в `src/judge.ts`). Провайдер
обязан вызвать `options.onPayload` и затем **нормализовать** результат:
перенести верхнеуровневый OpenAI-шный `response_format` в v2-форму
`model_options.response_format: {type: 'json_schema', schema, strict}`.

Без этой трансляции судья теряет strict-схему — а именно строгий JSON и есть
смысл судьи. Трансляция живёт в провайдере, а не в `src/pi.ts`: общий код не
должен знать особенности конкретного провайдера.

### Tool calling

- Запрос: pi-ai `Context.tools: [{name, description, parameters}]` →
  `tools: [{functions: {specifications: [{name, description, parameters}]}}]`.
- Ответ модели с вызовом: ассистентское сообщение содержит
  `content: [{function_call: {name, arguments}}]` и `tool_state_id`. Это
  отображается в pi-ai `ToolCall {type: 'toolCall', id, name, arguments}`.
- GigaChat не выдаёт отдельный идентификатор вызова, а pi-ai его требует.
  Идентификатор синтезируется из `tools_state_id` (при нескольких вызовах в
  одном сообщении — с индексом), чтобы на следующем ходу его можно было
  восстановить из самой истории, без внешнего состояния в провайдере.
- Результат инструмента: pi-ai `ToolResultMessage {toolCallId, toolName,
  content}` → сообщение с `content: [{function_result: {name, result}}]` и
  восстановленным `tools_state_id`.
- `stopReason` при наличии `function_call` — `toolUse`.

### Учёт токенов

v2 отдаёт `input_tokens` как полный размер промпта, внутри которого
`input_tokens_details.cached_tokens` — часть из кэша (в прогоне: `input_tokens:
17`, `cached_tokens: 2`). Потребитель в `src/pi.ts` считает вход как
`usage.input + usage.cacheRead + usage.cacheWrite`, поэтому маппинг должен быть
`input = input_tokens - cached_tokens`, `cacheRead = cached_tokens`,
`cacheWrite = 0` — иначе кэшированные токены посчитаются дважды.

### Завершение и ошибки

`finish_reason` GigaChat (`stop`, `length`, …) → pi-ai `StopReason`. Ошибки
приходят обычными HTTP-статусами (400/401/403/404/413/422/429/5xx, на 429 —
заголовок `Retry-After`) и пробрасываются как обычная ошибка вызова модели:
существующий код в `src/pi.ts` уже оборачивает их в понятное пользователю
сообщение и намеренно не сохраняет сырой текст ошибки провайдера.

## Потоковый вывод

Реального потока токен-за-токеном в v1 не делаем: запрос идёт одним вызовом, а
наружу выдаётся минимально достаточная последовательность событий pi-ai
(`start` → `text_start` → `text_end` → `done`, плюс события tool call, когда он
есть). Симулятору, судье и sandbox-агенту промежуточные дельты не нужны. В v2
GigaChat поток устроен как именованные SSE-события (`response.message.delta`,
`response.message.done`), так что при необходимости это добавляется позже без
смены контракта.

## Проверка TLS

Проверка серверного сертификата по умолчанию включена: с `GIGACHAT_CA_PATH` —
против этого CA bundle, без него — против системного доверенного хранилища
Node. Отключается только явно, через `GIGACHAT_INSECURE=1`, и такой запуск
логирует предупреждение.

Так сделано потому, что CA-цепочки внутреннего контура на руках нет (её нет и в
`agent_oc`, где просто стоит `verify_ssl_certs=False`), но тихо отключать
проверку — ровно то, от чего предостерегает внутренний референсный документ по
mTLS. Компромисс: небезопасный режим остаётся возможным, но всегда осознанным и
видимым. Молчаливого отката на запрос без сертификата при сбое mTLS нет.

Открытый вопрос, не блокирующий работу: проходит ли проверка против системного
хранилища без CA-файла — прогон делался сразу с `GIGACHAT_INSECURE=1`.

## Секреты

Боевые файлы сертификата и ключа никогда не попадают в git: в репозитории
фиксируются только имена переменных окружения. `.gitignore` дополнительно
закрывает `*.pem`, `*.key`, `*.cer`, `*.crt` и `/certs/` как страховку.

## Тестирование

- Юнит-тесты на чистые функции маппинга, без сети: сборка v2-запроса, разбор
  v2-ответа, трансляция `response_format`, маппинг tool calls в обе стороны,
  подсчёт токенов с кэшем. В духе принятого в проекте подхода с
  fake-реализациями вместо моков.
- Юнит-тест: без обязательных переменных окружения `createGigaChatProvider()`
  возвращает `undefined`.
- Ручная опциональная регрессия по существующему паттерну:
  `node --import tsx test/live/simulator-stop.ts gigachat GigaChat-2-Max`
  против настоящего внутреннего эндпоинта — не часть `npm test`.
- Отдельная ручная проверка sandbox-агента с инструментами на GigaChat, раз
  tool calling входит в объём: прогон учебного примера, где агент обязан
  вызвать инструмент.

## Нецели

- Ассистенты, треды и серверное хранение контекста GigaChat (`assistant_id`,
  `storage.thread_id`): Agent Lab ведёт историю сам и требует воспроизводимости.
- Встроенные инструменты GigaChat (`web_search`, `code_interpreter`,
  `image_generate` и прочие): испытуемому агенту разрешены только три
  зарегистрированных инструмента песочницы.
- Эмбеддинги, изображения, файлы-вложения.
- Переключение dev/prod URL по аналогии с Python-паттерном `DEV_MODE`: выбор
  «внешний или внутренний» уже делается самим `settings.provider`.
