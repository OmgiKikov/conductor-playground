# Agent Lab for Pi

Даёте Pi задачу, материалы и, если есть, реальные данные: golden set и обезличенные диалоги. Pi формирует цели пользователей, собирает карточки простых симулированных пользователей, вы проверяете и утверждаете их, затем симулятор разговаривает с агентом, а результат показывается с объективными проверками, оценками по рубрикам и вашими вердиктами. Испытуемым может быть песочный агент или ваш собственный агент по HTTP или из локального модуля.

Методика встроена в [скилл](skills/agent-builder/SKILL.md), промпты ролей и код проверки. Агенту не нужно читать статьи. План и разбор источников: [docs/PLAN.md](docs/PLAN.md). Глоссарий: [CONTEXT.md](CONTEXT.md).

## Запуск

Требуется Node.js 22.19+.

```sh
npm ci
npm run build
npm run pi
```

Последняя команда запускает Pi с подключёнными extension и скиллом. В Pi выберите модель через `/model`; при необходимости настройте провайдера через `/login`. Ключи не передаются в задаче или материалах.

Пример сообщения в Pi:

> Подготовь карточки пользователей для нашего агента переноса записей. Бизнес‑правила в @policy.md, golden set в @golden.json, обезличенные диалоги в @dialogues.json. Агент отвечает по HTTP на http://127.0.0.1:8080/agent, токен в переменной AGENT_TOKEN. Сравни статическую корзину, scripted и реактивного пользователя.

Pi вызовет `agent_lab_build`, подготовит черновик и остановится. Дальше всё через `/agent-lab`: проверка карточек, правка, подтверждение точной версии, запуск, разбор диалогов, ваши вердикты и итог.

## Что создаётся

- Требования с точными выдержками из материалов и открытые бизнес‑вопросы.
- Профили пользователей, извлечённые из реальных диалогов, с ссылками на диалоги‑доказательства.
- Карточки: цель, персона, характеристики, известные факты, поведение, первая реплика, лимит реплик, скрипт для scripted‑режима, критерий успеха, проверки и рубрики. Синтетические карточки берут персону только из профилей.
- Curated‑карточки из golden set без участия модели.
- Диалоги с полной трассой: реплики, вызовы инструментов, состояние, решения симулятора.
- Сводка доказательств: режимы пользователя, калибровка судьи, верность симулятора, ограничения.

## Подключение своего агента

`target` в задаче выбирает испытуемого.

```json
{ "kind": "http", "url": "http://127.0.0.1:8080/agent", "headersEnv": { "Authorization": "AGENT_TOKEN" }, "timeoutMs": 60000 }
```

На каждую реплику Agent Lab отправляет `POST` с телом:

```json
{ "sessionId": "trial-id", "scenarioId": "card-id", "initialState": { "records": {}, "writableFields": [] }, "messages": [{ "role": "user", "content": "..." }], "message": "текущая реплика" }
```

Ответ: строка или объект `{ "reply": "...", "events": [{ "tool": "lookup_record", "args": {}, "result": {} }], "records": { "A101": { "time": "14:00" } } }`. `events` попадают в трассу, `records` заменяют состояние мира перед объективными проверками. Значения заголовков читаются из переменных окружения в момент запроса и не сохраняются. Каждый ход отправляет всю историю; серверная сессия не требуется.

Локальный модуль:

```json
{ "kind": "module", "path": "/abs/path/agent.mjs", "exportName": "createSession" }
```

Модуль экспортирует `createSession({ sessionId, scenarioId, initialState })`, который возвращает объект с `respond(message, messages)` и необязательным `close()`. Справочный адаптер: [examples/echo-agent.mjs](examples/echo-agent.mjs). Модуль исполняется в процессе Pi доверенным оператором; путь должен быть абсолютным.

Состояние, которое вернул внешний агент, это **сообщённое** состояние: его никто не наблюдал доверенным кодом. Отчёт помечает это в каждом диалоге.

## Импорт golden set и реальных диалогов

```json
{
  "task": "Проверить агента переноса записей",
  "materials": [{ "name": "policy.md", "content": "..." }],
  "mode": "live",
  "target": { "kind": "sandbox" },
  "settings": { "userModes": ["static", "scripted", "reactive"], "repeats": 1 },
  "goldenCases": [{
    "id": "gold_move", "goal": "Перенести запись A101 на 14:00", "opening": "Перенесите мою запись A101 на 14:00",
    "successCriteria": "Запись A101 стоит на 14:00", "script": ["Да, на 14:00."],
    "initialState": { "records": { "A101": { "time": "09:00" } }, "writableFields": ["time"], "transientFailures": 0 },
    "checks": [{ "id": "time", "kind": "state_equals", "description": "Время изменено", "recordId": "A101", "field": "time", "value": "14:00" }]
  }],
  "dialogues": [{ "id": "d1", "messages": [{ "role": "user", "content": "перенесите A101 на 14" }, { "role": "assistant", "content": "Готово." }], "outcome": "success" }]
}
```

Golden cases становятся карточками с provenance `curated` и сохраняют свои проверки и рубрики. Диалоги дают профили: модель видит только реплики пользователя и обязана ссылаться на реальные `id`. При наличии профилей синтетические карточки выбирают `profileId`, а текст персоны копируется из профиля. Так модель не может приукрасить пользователя.

## Режимы пользователя

`settings.userModes` перечисляет, кто играет пользователя на одних и тех же карточках:

- `static`: только первая реплика. Это обычная тестовая корзина.
- `scripted`: реплики из `user.script` по порядку, без реакции на ответы агента. Карточки без скрипта пропускаются с пометкой.
- `reactive`: модель отвечает на реальные реплики агента в рамках лимита `maxFollowUps` и может уйти, как реальный пользователь.

Сводка показывает по каждому режиму долю пройденных диалогов, число реплик, вызовы и стоимость, а также проверки, которые провалились только в этом режиме. Это и есть ответ на вопрос, что реактивный симулятор находит сверх корзины и скриптов. Сравнительный workflow с baseline и кандидатом использует ровно один режим.

## Калибровка судьи и верность симулятора

Оценки модели по рубрикам хранятся отдельно от ваших вердиктов. По каждой метрике и проверке считается согласие с последним вердиктом человека. Положительный класс это ошибка агента: TPR показывает, какую долю подтверждённых человеком ошибок судья тоже назвал ошибкой, TNR какую долю подтверждённых успехов он тоже пропустил. Меньше 60 размеченных пар помечается как недостаточно данных.

Верность симулятора считается по реактивным диалогам против загруженных реальных: реплик на диалог, длина реплики, доля вопросов, доля ушедших пользователей, и разрыв по каждой метрике. Отдельно показывается, сколько ваших вердиктов по рубрикам симулятора прошло. Малый разрыв не доказывает реализм, большой его опровергает.

## Как устроена проверка

Раздельные сессии Pi извлекают требования, профили, проектируют карточки и строят агента. Каждый диалог начинается с нового состояния и новой сессии. Фактические действия оценивает доверенный код; для внешнего агента используется сообщённое состояние. Вложенные сессии не имеют shell, файловых и сетевых инструментов и не подхватывают сторонние extensions, skills и AGENTS‑файлы.

Человек обязателен в двух точках: подтверждение точной версии черновика до диалогов и вердикты по результатам после. Изменение утверждённых условий требует нового прогона.

## Границы этой версии

- Синтетические результаты не доказывают качество с реальными пользователями. Даже профили из реальных диалогов заземляют только промпт.
- Сообщённое внешним агентом состояние не наблюдается доверенным кодом.
- Судья не откалиброван, пока вы не разметите достаточно диалогов. Сводка это показывает.
- Метрики верности описательные. Обученных симуляторов и метрики USI здесь нет.
- Сравнение двух версий внешнего агента по HTTP не поддерживается; сравнительный workflow меняет только AgentSpec песочного агента.
- Один активный эксперимент на каталог данных.

## Проверка без API

```sh
npm test
npm run demo -- --data-dir .context/demo
```

Демо использует скриптовых актёров, детерминированные профили и ремонт отсутствующего инструмента. Оно проверяет тот же полный цикл, включая режимы пользователя, внешний модульный адаптер, настоящие изменения тестовых записей и сохранение доказательств. Это демонстрация механики, а не измеренное улучшение LLM.

## Необязательный CLI

```sh
node dist/cli.js status
node dist/cli.js build --input task.json
node dist/cli.js prepare --input task.json
node dist/cli.js export --id EXPERIMENT_ID --output evidence.json
```

`task.json` содержит `task`, `materials`, `mode`, `settings`, `target`, `goldenCases`, `dialogues` и необязательный `existingAgent`. `build` и `prepare` только сохраняют черновик; подтверждение и запуск делаются в Pi через `/agent-lab`. Экспорт включает запись эксперимента, сводку доказательств и журнал трасс.

Материалы и диалоги сохраняются локально открытым текстом с ограниченными правами файлов. В live‑режиме необходимое содержимое отправляется выбранному провайдеру модели. Секреты внешнего агента живут в переменных окружения и в записи не попадают.
