# Agent Lab

Проверьте, что сломала правка вашего AI-агента. Откройте его проект, опишите задачу обычными словами и получите воспроизводимый тест с доказательством результата.

```sh
npm ci
npm start
```

Нужен Node.js 22.19+ и настроенная модель в Pi. Agent Lab использует установленный Pi и его авторизацию. Для команды `agent-lab` выполните `npm link` в этом репозитории, затем перейдите в проект своего агента; `node /абсолютный/путь/к/agent-lab/dist/cli.js` делает то же без глобальной установки.

Напишите в открывшемся терминале:

> Проверь агента в этой папке. После уточнения клиентом времени он иногда сохраняет старое значение.

Agent Lab прочитает проект, найдёт точку входа и подготовит один небольшой тест. Покажет запрос, ожидаемый результат, подключение и лимиты. После подтверждения запуска выполнит диалог и объяснит результат по реальным репликам или состоянию.

Дальше можно продолжить разговор:

- «Почему этот тест упал? Покажи конкретную реплику».
- «Здесь ошибся сам тест: пользователь не сообщал это значение».
- «Исправь промпт агента, чтобы он учитывал последнее уточнение».
- «Проверь исправление на том же случае».
- «Сохрани этот случай как регрессионный тест».

Подтверждение запуска разрешает выполнение в показанных пределах. Оно не записывает выдуманную ручную проверку ожиданий или вердикт человека. Исходные результаты сохраняются; изменение условий не выдаётся за улучшение агента.

## Попробовать без модели

```sh
npm run build
node dist/cli.js chat --offline
```

В терминале введите `/agent-lab demo`. Учебный агент умеет читать записи, но ему недоступно изменение: сравните обычное действие, изменение запроса по ходу диалога и проверку сохранности записи. После запуска `r` создаёт повтор, `e` позволяет включить инструмент изменения, `d` показывает сравнение. Акторы демо детерминированы; это пример рабочего цикла, а не измерение качества LLM.

## Повторять сохранённые тесты

Полезный тест можно сохранить из разговора или через CLI:

```sh
agent-lab save-suite --id RUN_ID --output .evals/regression.json
agent-lab evaluate --input .evals/regression.json --yes
```

`--case SCENARIO_ID` выбирает один случай; флаг можно повторять. Определение тестов сохраняет источники, исходную проверку и происхождение. Результаты и разрешение запуска каждый раз новые. Существующий файл не перезаписывается. Добавьте проверенное определение в Git; локальные подключения содержат пути, которые нужно настроить для машины CI.

`evaluate` использует модель, подключение и лимиты из файла, сохраняет JSON, HTML и трассы. Коды возврата: `0` — заданные оценки пройдены; `1` — зарегистрирован провал; `2` — ошибка измерения или неполные данные. Оценки модели остаются предварительными. В CI сохраните каталог `.agent-lab/exports` как артефакт запуска.

## Проверить самого судью

В новых живых прогонах из разговора судья — OpenRouter `openai/gpt-5.6-sol`, с маршрутом `openai` без переключения поставщика. Он настраивается отдельно от модели планировщика и симулятора:

```json
{"settings":{"judge":{"provider":"openrouter","model":"openai/gpt-5.6-sol","upstream":"openai"}}}
```

Каждая применимая рубрика получает два отдельных вызова при `temperature=0`; в одном запросе судья видит только одну рубрику. Судья отдельно рассматривает условия успеха и провала. Код выдаёт решающий результат только при непротиворечивых условиях и совпадении двух вердиктов; иначе — `unknown`. Это защита от части шума, а не доказательство правильности. По два вызова на рубрику расходуют общий бюджет прогона; лимит автоматически не повышается. Другие провайдеры поддерживаются без поля `upstream`; в существующих конфигурациях без `judge` обычный прогон использует выбранную общую модель.

Для измерения воспроизводимости на сохранённом живом прогоне:

```sh
node dist/cli.js audit-judge --id RUN --output judge-audit-001 --repeats 10 --yes
```

Команда не вызывает испытуемого и не меняет исходные оценки. Один повтор содержит по два запроса на каждую применимую рубрику: десять повторов — до двадцати запросов на рубрику и диалог. Можно выбрать карточки через `--case ID`. Лимиты вызовов и времени берутся из прогона; ошибки занимают свою попытку и не заменяются удачной. После трёх подряд неудачных оценок аудит останавливается, сохраняя отчёт и пропуски. Если отдельный судья не был сохранён, аудит использует OpenRouter GPT‑5.6 Sol / OpenAI. Явно сохранённая модель исторического прогона сохраняется. Каталог вывода должен быть новым.

`report.md` показывает разброс каждой рубрики на каждом неизменном входе; `statistics.json` — числители, знаменатели и ошибки. Все пары ответов перекрываются, поэтому отдельно считаются непересекающиеся пары. Нулевой наблюдаемый шум на малой выборке не подтверждает пригодность для сравнения. Стабильный `unknown` тоже не означает готовность рубрики.

Исходные запросы, ответы до разбора JSON, незавершённые запросы и ошибки сохраняются в журнал. Исправления JSON для судьи отключены. В обычном прогоне эти данные доступны в `trial.judgeAudit`, JSON/HTML-экспорте и `.trace.jsonl`; после прерывания ориентируйтесь на последнюю запись журнала для каждой попытки. Файлы содержат те же материалы и диалоги, что и прогон.

Сравнение не считает неопределённость успехом, требует применимой оценки симулятора и одинаковой версии протокола/модели судьи. Совпавшие ответы с различающимися оценками требуют разбора и не засчитываются исправлением. Старые живые оценки без протокола сохраняются для просмотра, но не подтверждают улучшение. Противоречия в бизнес-правилах остаются решениями владельца; повторные вызовы модели их не разрешают.

Коды завершения `audit-judge`: 0 — выбранный потолок шума подтверждён на измеренных входах при допущениях отчёта; 1 — есть неопределённость, шум или недостаточно повторов; 2 — ошибки или неполный прогон. Это не сертификат правильности судьи. Для `ready` команда учитывает одновременную проверку всех измеренных входов и рубрик; пока реализована точная граница для нулевого числа расхождений в непересекающихся парах.

OpenRouter-судья использует Chat Completions с `response_format: json_schema`; числовые и размерные ограничения дополнительно проверяются локально. В `judgeAudit.transport` видны API, запрошенный поставщик и применение структурированного формата. Сохранённые разобранные оценки проверяются повторно по исходному ответу. Адаптер Chat Completions выбирается явно, чтобы настройки маршрутизации OpenRouter применялись независимо от API в каталоге модели.

Методика адаптирована из [ai-evals-course/evals-skills](https://github.com/ai-evals-course/evals-skills): сначала разбор полных трасс, затем конкретные критерии и проверка судьи. [Что перенесено и что остаётся непроверенным](docs/EVALS-METHOD.md).

Сверка с ручными вердиктами показывает отдельные строки для разных формулировок и версий судьи, число ручных pass/fail, решающие оценки, unknown и пропуски. Последние остаются в знаменателях TPR/TNR. Поле `sampleSufficient` означает только наличие хотя бы 30 меток каждого класса; `validationStatus` остаётся `not_established`, поскольку текущие ручные разборы не являются отложенной выборкой для валидации судьи. Эти данные не подменяют измерение повторяемости.
