# Agent Lab for Pi

Для текущего PoC укажите Pi локальный проект с готовым агентом. Pi читает код, README, промпты и конфигурацию запуска, подбирает локальное подключение и собирает материалы для карточек. Вы проверяете и утверждаете карточки, затем симулятор разговаривает с агентом, а результат показывается с объективными проверками, оценками по рубрикам и вашими вердиктами. Основной путь — локальный процесс или модуль; подключение по HTTP можно использовать позже.

Реальные данные необязательны: можно просто накидать вводных про пользователей, и билдер соберёт синтетические карточки. Итог всегда показывает, какая доля результата держится на синтетике, и понижает доверие, пока нет golden set или реальных диалогов.

Методика встроена в [скилл](skills/agent-builder/SKILL.md), промпты ролей и код проверки. Агенту не нужно читать статьи. План и разбор источников: [docs/PLAN.md](docs/PLAN.md). Глоссарий: [CONTEXT.md](CONTEXT.md).

## Простой путь

1. Укажите папку проекта с агентом и накидайте вводных: кто пользователи, чего хотят, где обычно ломается. По скиллу Pi сам изучает проект, готовит `command`/`module` и при необходимости небольшой адаптер к существующему агенту. Вручную собирать JSON подключения и копировать материалы не нужно; golden set и реальные диалоги необязательны.
2. Откройте `/agent-lab`, просмотрите карточки, нажмите `r`.
3. Прочитайте ИТОГ: сколько диалогов пройдено, где агент слаб, насколько этому верить и что сделать дальше.

Всё остальное, режимы пользователя, калибровка судьи и верность симулятора, лежит в секции «4 Статистика» и в отчёте. Оно нужно, когда доверие к итогу низкое и надо понять почему. `preset: "thorough"` включает все режимы и два повтора без ручных настроек.

Как считается доверие. Низкое: меньше 5 диалогов с объективными проверками, или все карточки синтетические, или больше четверти диалогов невалидны. Среднее: есть golden или реальные карточки, но аудит человеком не завершён, часть провалов без вердикта, или выборка меньше 30 диалогов. Высокое: аудит завершён, у каждого провалившегося диалога есть решающий вердикт человека (пройдено или не пройдено), от 30 оценённых диалогов, невалидных нет. Порог в 30 не выдуман: разбор ошибок работает на десятках трасс, а не на единицах, поэтому меньшая выборка может быть верной, но называться проверенной не может. Вердикты «неясно» и «невалидно» ничего не решают: они остаются причиной неопределённости и держат доверие на среднем. Оценки модели по рубрикам, включая диалоги без объективных проверок, показываются отдельно как непроверенные и в слабые места попадают, но высокого доверия сами по себе не дают.

## Запуск

Требуется Node.js 22.19+.

```sh
npm ci
npm run build
npm run pi
```

Последняя команда запускает Pi с подключёнными extension и скиллом. В Pi выберите модель через `/model`; при необходимости настройте провайдера через `/login`. Ключи не передаются в задаче или материалах.

Пример сообщения в Pi:

> Проверь готового агента в /abs/path/my-agent. Посмотри код, README и промпты, найди способ запустить его локально и подготовь пять карточек. Пользователи часто спешат и забывают ID записи. Реальных диалогов пока нет.

Pi изучит проект своими файловыми инструментами, соберёт материалы и параметры подключения, затем вызовет `agent_lab_build` и подготовит черновик. Дальше всё через `/agent-lab`: проверка карточек, правка, подтверждение точной версии, запуск, разбор диалогов, ваши вердикты и итог. Чтение кода помогает понять устройство агента и возможные места ошибок; правильность его поведения проверяется в диалогах по утверждённым требованиям. Выводы из реализации остаются допущениями для проверки владельцем.

## Что создаётся

- ИТОГ: пройдено X из Y, слабые места, доверие к результату с причинами, следующие шаги. Он первый на доске, в отчёте и в ответе Pi.
- Требования с точными выдержками из материалов и открытые бизнес‑вопросы.
- Профили пользователей: написанные вами вручную (помечены как owner) и извлечённые из реальных диалогов со ссылками на диалоги‑доказательства.
- Карточки: цель, персона, характеристики, известные факты, поведение, первая реплика, лимит реплик, скрипт для scripted‑режима, критерий успеха, проверки и рубрики. Синтетические карточки берут персону только из профилей.
- Curated‑карточки из golden set без участия модели.
- Диалоги с полной трассой: реплики, вызовы инструментов, состояние, решения симулятора.
- Сводка доказательств: режимы пользователя, калибровка судьи, верность симулятора, ограничения.

## Подключение своего агента

В локальном PoC Pi выбирает `target` после чтения проекта. Ниже — контракты для адаптера; пользователю достаточно указать репозиторий. HTTP нужен, когда агент проверяется как отдельный сервис.

```json
{ "kind": "http", "url": "http://127.0.0.1:8080/agent", "headersEnv": { "Authorization": "AGENT_TOKEN" }, "timeoutMs": 60000 }
```

На каждую реплику Agent Lab отправляет `POST` с телом:

```json
{ "sessionId": "trial-id", "scenarioId": "card-id", "initialState": { "records": {}, "writableFields": [] }, "messages": [{ "role": "user", "content": "..." }], "message": "текущая реплика" }
```

Ответ: строка или объект `{ "reply": "...", "events": [{ "tool": "lookup_record", "args": {}, "result": {} }], "records": { "A101": { "time": "14:00" } } }`. `events` попадают в трассу, `records` заменяют состояние мира перед объективными проверками. Значения заголовков читаются из переменных окружения в момент запроса и не сохраняются. Каждый ход отправляет всю историю; серверная сессия не требуется.

Локальный модуль:

```json
{ "kind": "module", "path": "/abs/path/agent.mjs", "exportName": "createSession" }
```

Модуль экспортирует `createSession({ sessionId, scenarioId, initialState })`, который возвращает объект с `respond(message, messages)` и необязательным `close()`. Справочный адаптер: [examples/echo-agent.mjs](examples/echo-agent.mjs). Модуль исполняется в процессе Pi доверенным оператором; путь должен быть абсолютным.

Локальный процесс, например агент на Python, без HTTP:

```json
{ "kind": "command", "command": "python3", "args": ["/abs/path/agent.py"], "timeoutMs": 60000 }
```

На каждый диалог Agent Lab запускает процесс и общается JSON‑строками: в stdin приходит `{"type":"respond", "sessionId", "scenarioId", "initialState", "messages", "message"}`, в stdout ожидается одна строка с ответом в том же формате, что и для HTTP; в конце приходит `{"type":"close"}`. Зависший процесс убивается по таймауту, упавший показывает код выхода и хвост stderr. Справочный адаптер: [examples/echo-agent.py](examples/echo-agent.py), достаточно заменить в нём функцию `handle` вызовом вашего RAG‑агента.

Состояние, которое вернул внешний агент, это **сообщённое** состояние: его никто не наблюдал доверенным кодом. Отчёт помечает это в каждом диалоге.

## Пилот на реальном RAG‑агенте: восемь шагов

| Шаг | Что нужно от вас | Что делает Agent Lab |
|---|---|---|
| 1. Выбрать агента | Папка локального проекта с готовым агентом. | Pi читает код и конфигурацию, готовит локальный `command`/`module`; Agent Lab открывает сессию на каждый диалог и пишет трассу. |
| 2. Карточка агента | Уточнить назначение агента, если оно не описано в проекте. | Pi собирает материалы из README, промптов и документации; Agent Lab извлекает требования с цитатами и готовит карточки на проверку. |
| 3. Поведение на проме | Выгрузка логов как `dialogues`: `[{ "id", "messages": [{ "role", "content" }], "outcome" }]`. | Считает стиль реплик и долю ушедших пользователей; сравнивает с симуляцией. |
| 4. Паттерны пользователей | Те же логи. При желании свои типы в `profiles`. | Извлекает профили: персона, характеристики, наблюдаемый стиль, ссылки на диалоги. |
| 5. Цели пользователей | Те же логи. | Извлекает цели реальных пользователей и делает production‑карточки, открытые их собственными репликами. |
| 6. Модель пользователя | Проверить и поправить карточки в `/agent-lab`. | Карточка = цель, персона, характеристики, факты, поведение, первая реплика, лимит реплик. Синтетика добавляет то, чего нет в логах. |
| 7. Диалог с агентом | Нажать `r`. | Реактивный симулятор разговаривает с агентом; при желании ещё статический и scripted режимы. |
| 8. Оценка | Прочитать ИТОГ, поставить вердикты по провалам: `p` пройдено, `n` не пройдено, `v` подробно. | Ставит провалы без вердикта первыми и считает, сколько осталось. Объективные проверки, рубрики (цель, периметр, верность симулятора), доверие с причинами, калибровка судьи. |

Формат логов нарочно минимальный. Если выгрузка в CSV или JSONL с другими полями, попросите Pi привести её к этому JSON перед вызовом `agent_lab_build`.

## Импорт golden set и реальных диалогов

```json
{
  "task": "Проверить агента переноса записей",
  "materials": [{ "name": "policy.md", "content": "..." }],
  "mode": "live",
  "target": { "kind": "sandbox" },
  "notes": "Клиенты часто пишут в спешке и не помнят ID записи. Бывают раздражённые.",
  "profiles": [{ "id": "hurried", "persona": "Клиент в спешке", "characteristics": ["Пишет коротко", "Не помнит ID записи"] }],
  "settings": { "userModes": ["static", "scripted", "reactive"], "repeats": 1 },
  "goldenCases": [{
    "id": "gold_move", "goal": "Перенести запись A101 на 14:00", "opening": "Перенесите мою запись A101 на 14:00",
    "successCriteria": "Запись A101 стоит на 14:00", "script": ["Да, на 14:00."],
    "initialState": { "records": { "A101": { "time": "09:00" } }, "writableFields": ["time"], "transientFailures": 0 },
    "checks": [{ "id": "time", "kind": "state_equals", "description": "Время изменено", "recordId": "A101", "field": "time", "value": "14:00" }]
  }],
  "dialogues": [{ "id": "d1", "messages": [{ "role": "user", "content": "перенесите A101 на 14" }, { "role": "assistant", "content": "Готово." }], "outcome": "success" }]
}
```

Golden cases становятся карточками с provenance `curated` и сохраняют свои проверки и рубрики. `notes` это ваши вводные своими словами: генератор карточек берёт их как полноправный вход, помечает взятые из них факты как допущения владельца и не превращает в бизнес‑правила. `profiles` это типы пользователей, которые вы описали сами; они помечены `source: "owner"`. Диалоги дают наблюдённые профили: модель видит только реплики пользователя и обязана ссылаться на реальные `id`. При наличии любых профилей синтетические карточки выбирают `profileId`, а текст персоны копируется из профиля. Так модель не может приукрасить пользователя, а вы сохраняете право описать его сами.

## Режимы пользователя

`settings.userModes` перечисляет, кто играет пользователя на одних и тех же карточках:

- `static`: только первая реплика. Это обычная тестовая корзина.
- `scripted`: реплики из `user.script` по порядку, без реакции на ответы агента. Карточки без скрипта пропускаются с пометкой.
- `reactive`: модель отвечает на реальные реплики агента в рамках лимита `maxFollowUps` и может уйти, как реальный пользователь.

Сводка показывает по каждому режиму долю пройденных диалогов, число реплик, вызовы и стоимость, а также проверки, которые провалились только в этом режиме. Это и есть ответ на вопрос, что реактивный симулятор находит сверх корзины и скриптов. Сравнительный workflow с baseline и кандидатом использует ровно один режим.

## Калибровка судьи и верность симулятора

Оценки модели по рубрикам хранятся отдельно от ваших вердиктов. По каждой метрике и проверке считается согласие с последним вердиктом человека. Положительный класс это ошибка агента: TPR показывает, какую долю подтверждённых человеком ошибок судья тоже назвал ошибкой, TNR какую долю подтверждённых успехов он тоже пропустил. Меньше 60 размеченных пар помечается как недостаточно данных.

Верность симулятора считается по реактивным диалогам против загруженных реальных: реплик на диалог, длина реплики, доля вопросов, доля ушедших пользователей, и разрыв по каждой метрике. Отдельно показывается, сколько ваших вердиктов по рубрикам симулятора прошло. Малый разрыв не доказывает реализм, большой его опровергает.

## Как устроена проверка

Раздельные сессии Pi извлекают требования, профили, проектируют карточки и строят агента. Каждый диалог начинается с нового состояния и новой сессии. Фактические действия оценивает доверенный код; для внешнего агента используется сообщённое состояние. Вложенные сессии не имеют shell, файловых и сетевых инструментов и не подхватывают сторонние extensions, skills и AGENTS‑файлы.

Человек обязателен в двух точках: подтверждение точной версии черновика до диалогов и вердикты по результатам после. Изменение утверждённых условий требует нового прогона.

## Границы этой версии

- Синтетика полноправный вход, но не единственная правда: итог называет её долю и держит доверие низким, пока нет golden set или реальных диалогов. Даже профили из реальных диалогов заземляют только промпт.
- Сообщённое внешним агентом состояние не наблюдается доверенным кодом.
- Судья не откалиброван, пока вы не разметите достаточно диалогов. Сводка это показывает.
- Метрики верности описательные. Обученных симуляторов и метрики USI здесь нет.
- Сравнение двух версий внешнего агента по HTTP не поддерживается; сравнительный workflow меняет только AgentSpec песочного агента.
- Один активный эксперимент на каталог данных.

## Проверка без API

```sh
npm test
npm run demo -- --data-dir .context/demo
```

Демо использует скриптовых актёров, детерминированные профили и ремонт отсутствующего инструмента. Оно проверяет тот же полный цикл, включая режимы пользователя, внешний модульный адаптер, настоящие изменения тестовых записей и сохранение доказательств. Это демонстрация механики, а не измеренное улучшение LLM.

## Необязательный CLI

```sh
node dist/cli.js status
node dist/cli.js build --input task.json
node dist/cli.js prepare --input task.json
node dist/cli.js export --id EXPERIMENT_ID --output evidence.json
```

`task.json` содержит `task`, `materials`, `mode`, `settings`, `target`, `goldenCases`, `dialogues` и необязательный `existingAgent`. `build` и `prepare` только сохраняют черновик; подтверждение и запуск делаются в Pi через `/agent-lab`. Экспорт включает запись эксперимента, сводку доказательств и журнал трасс.

Материалы и диалоги сохраняются локально открытым текстом с ограниченными правами файлов. В live‑режиме необходимое содержимое отправляется выбранному провайдеру модели. Секреты внешнего агента живут в переменных окружения и в записи не попадают.
