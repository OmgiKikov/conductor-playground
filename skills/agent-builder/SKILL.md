# Agent builder

Work directly in this Pi conversation. For the current PoC, start from the owner's local agent repository: read its code and prepare a local connection with the outer Pi tools. HTTP integration is an optional later path, not a prerequisite. `agent_lab_build` prepares a draft from the task, material names/full contents, optional existing AgentSpec, a target (local command/module, sandbox or HTTP), optional golden cases and optional de-identified real dialogues, using the current Pi model unless settings override it. settings.userModes may list static, scripted and reactive so the same cards run under each user side; preset=thorough sets all three with two repeats. notes and profiles carry the owner's own hints and user types. The default workflow evaluates one agent; it does not run dialogues, approve its own draft or optimize the agent automatically. The human opens `/agent-lab` to review and approve cards, run the evaluation, inspect results and record their review.

## Start from the local project

- Use the repository the owner named, or the current workspace when it contains the intended agent. Read its README, dependency/run configuration, entry point, prompts, tools and relevant tests to understand the actual call flow and session state. Find these details yourself before asking the owner; ask for a path only when the intended project is unavailable or ambiguous.
- Reuse an existing callable entry point. Choose `command` for a local process such as Python, or `module` for a compatible JavaScript session factory. If the contract needs a wrapper, write the smallest adapter that calls the real agent; use the project's interpreter/environment and absolute paths, setting `cwd` when its imports or data depend on it. Preserve state between turns and reset it between dialogues. Keep JSON replies on stdout and diagnostic logs on stderr. Show the chosen entry point and command with the draft. Do not substitute a scripted echo or rebuild the agent as an AgentSpec. The existing command/module contracts are documented in the package README.
- Collect relevant documented requirements, declared prompt behavior and user-facing knowledge into `materials` with original file names and exact excerpts; the owner need not paste files or hand-write target JSON. Read implementation code to understand capabilities and likely failure cases, but do not promote its current behavior or test expectations into unquestionable business rules. Mark inferred expectations as provisional for draft review and surface contradictions. Keep credentials out of materials. Pass the owner's hints as `notes`; golden data and production logs are optional for this PoC.

Code inspection prepares the connection and scenarios; evidence about the agent still comes from running it. Before model preparation, Agent Lab statically checks the executable/PATH, working directory, entry file and required header environment variables. This does not import a module, launch a process or send a probe message. Do not send a supposedly safe test request before the owner's approval: even a greeting can cause an unknown agent to act. Nested card generation works from the extracted requirements, and the simulator receives only the approved user's knowledge. The outer Pi session may return to the code to explain a failure after inspecting its trace.

## Conversation and native board

The user can start with `/agent-lab /path/to/project`, or `n` in the experiment list. `/agent-lab demo` or `d` in the list opens the built-in example without a model provider. `a` on a card or result returns to this Pi conversation with the user's own request and hidden Agent Lab context identifying the selected experiment, scenario or trial. The board releases its writer lock before this turn starts. Read fresh evidence using `agent_lab_inspect`; do not guess which experiment the user means or treat the hidden context as human approval.

Keep the ordinary conversation free of JSON. After preparation, summarize the proposed situations in plain language and explain that Enter opens the prefilled board command. After a correction, name what changed and what still needs the owner's decision. For open business questions or a failed preparation, read the saved evidence file, add the supplied corrections to the materials and build a new draft while preserving the old one. Never invent missing answers.

To edit cards, inspect the current draftHash and send only the changed complete cards in `patch.scenarios`. Cards with matching IDs update in place; new IDs add cards; omitted cards stay unchanged. Deletion requires explicit `removeScenarioIds` and must match the owner's intended removal. Never use a new ID to rename an existing card or imply deletion by omission. Duplicate IDs, unknown removals, update/remove conflicts and an empty resulting set are rejected without saving. Summarize how many cards changed or were removed. A stale hash requires a fresh inspection before retrying.

For a result discussion, inspect the selected trial's actual trace. Lead with the concrete failure, cite the trial and event numbers, distinguish the agent from simulator/infrastructure problems, say whether a human confirmed the finding, and propose the next useful action. A suspected code cause must be labelled a hypothesis until checked. Do not bury the finding under general statistics or a request for more data. Do not change the external agent unless the user explicitly asks to fix it. Tools prefill the return command without replacing unfinished user text.

## Working protocol

1. **Derive user goals.** Collect the task, sources, existing AgentSpec, the target, golden cases and de-identified real dialogues when available. A target may be the sandbox, an http endpoint, a module, or a command (a local process such as python3 agent.py speaking JSON lines); an agent card describing the perimeter belongs in the materials. Real failures and golden cases carry the most weight when they exist. Without them, the owner's notes (their own words about users, goals and where things break) and hand-written profiles are a legitimate start: synthetic cards are a normal way to begin, and the verdict always states how much of the evidence is synthetic. Pass such hints as notes and profiles; never silently turn them into business rules. Read authorized local materials with the outer Pi session. Extract requirements with exact source quotations, then express concrete outcomes the user wants; an instruction to call a tool is not itself a user goal. Each card states observable success criteria. Ask only for missing business decisions or contradictions that block the task. Do not invent source quotations, business policy or optional production requirements. Sandbox tool semantics are trusted execution facts, not quotable business sources.
2. **Prepare a simple user model.** Generate the requested number of cards, five by default, independently of the agent implementation. When real dialogues were supplied, observed profiles are extracted from user turns only. Profile extraction may return no profiles when there is too little evidence. Both profileId and persona are optional: use goal, facts and behavior alone when sufficient or requested. A linked card copies persona and characteristics from its profile; production goals do not require a profile either. A card may carry a script of user lines for scripted mode. Real dialogues also yield production cards: observed goals opened with the real user's own message and the observed profile; synthetic cards then cover what the logs do not, including an out-of-scope request when the materials describe the perimeter. A card contains goal, known facts, behavior, opening, follow-up limit, assumptions, applicable initial state/checks and explicit metric rubrics; add persona and relevant characteristics only when useful and supported. A persona is an interaction role and context, not an invented demographic profile. Label synthetic fixture facts and necessary assumptions. Use code checks for literal requirements and an agent-goal rubric for semantic requirements. Do not add a rubric that duplicates an exact text comparison. Keep simulator fidelity separate; the harness adds that rubric for generated external cards. A conversational agent may use no tools or deterministic checks. Show the draft in Pi; use `agent_lab_edit` only for draft changes requested or needed before review. To correct a shared profile, inspect its original fields and draftOverride, then send profileEdits:[{id,override:{persona,characteristics}}] with the current expectedHash. The override replaces the previous override; omitted fields use the original. persona:null removes persona, characteristics:[] removes traits, and override:null restores the original. All linked cards update together; original source/evidence remain unchanged. Never call an edit a human judgment. For a separate card persona, remove profileId first.
3. **Run dialogue after human review.** Direct the human to `/agent-lab` to inspect goals, personas, facts, assumptions, criteria, agent and budget, edit them and approve the exact draft. The model cannot provide that approval or bypass it through an internal run method. Actual unresolved business questions remain blockers. The approved suite is frozen before running. Each target session receives its own dialogue and reset state; the user simulator responds to the actual agent reply. Preserve follow-up and global call/turn/time limits, tool results, cancellation reasons and traces.
4. **Evaluate and review the result.** Lead with a concrete finding and the next action. Distinguish run completion, code-check outcomes, provisional rubric estimates and human review: an invalid trial is an infrastructure/simulator problem, not a measured agent failure or a pass. State the measured/planned denominator and unresolved failures. Evidence quality is separate from whether the agent succeeded; a confirmed smoke failure is still useful evidence. Bring user modes, calibration and fidelity only when they explain the finding or the user asks. The evidence summary adds per-user-mode results with the failures only the reactive simulator found, judge calibration against human verdicts (TPR and TNR with fail as the positive class; fewer than sixty labeled pairs is flagged as insufficient) and simulator fidelity gaps against the supplied real dialogues. Present all of them as observations. A separate no-tool model session assesses the approved rubric against actual trace/state and cites event sequence IDs. Its pass/fail/unknown result is provisional; it does not rewrite deterministic outcomes. Show failure reasons, missing evidence, calls, time, cost and trace links. Use `agent_lab_inspect` to open the returned experiment and trial IDs. The human uses `/agent-lab` to audit representative successful and unsuccessful dialogues and annotate disputed checks/metrics. Every pending agent failure needs a decisive verdict before finalization; unknown/invalid notes do not resolve that queue. Preserve both original evidence and the human review. Changes to criteria require a new reviewed run, not rewriting the measured result.

5. **Repeat after a change.** Use `agent_lab_repeat` on the reviewed run to prepare an exact copy of its suite, not newly generated cards. Set `targetVersion` through `agent_lab_edit` before the next human confirmation. Local entry points and tracked Git changes are fingerprinted; remote services, environment variables and untracked dependencies still require the operator to identify the tested release. In Pi, `r` repeats a finished run, `d` compares it with its parent, `/` searches, `u` filters pending failures, and `x` exports an offline HTML report. Comparisons reject altered criteria/settings, duplicates and inconsistent evidence. Missing or invalid attempts exclude the matching pair on both sides; only identical scenario/mode/repeat keys are compared. Report valid/planned pairs and excluded counts prominently. A partial comparison describes the paired subset and cannot establish overall improvement. Rubric-only failures participate but remain provisional. High confidence requires distinct, diverse, individually reviewed cards; repeated paraphrases are not independent evidence.

Select live mode only with an authenticated Pi model. The built-in no-provider demonstration is available from the `/agent-lab` experiment list and uses the same evaluate, review, repeat and comparison flow. From a conversation, call `agent_lab_build` with `mode:"demo"` and omit task/materials; its actors and assessments are scripted and demonstrate mechanics, not model quality. Both paths prepare a draft for human review. The exported AgentSpec configures this package's conversation and trusted record tools; it is not a separately installed production agent. External agents connect through target kind http (POST JSON with sessionId, scenarioId, initialState, messages and message; the reply may include events and records; header values come from environment variables named in headersEnv) or kind module (an absolute path exporting createSession, whose session exposes respond and close). Records an external agent returns are reported state, not state observed by trusted code; say so whenever you interpret its checks.

## Interpretation

For externally connected agents, generated cards use observable text checks and/or semantic agent rubrics, plus a fixed harness-provided simulator-fidelity rubric. When literal checks fully express the goal, generated metrics may be empty: do not ask a model to repeat a deterministic comparison. Semantic requirements still need an agent rubric. The generator has no external state/tool contract, so it must not invent records or tool checks. It may generate observable answer checks only for literal requirements grounded in cited materials or an explicit exact user request. `answer_equals` compares the last assistant reply exactly, including case, spaces and newlines; use it when the whole final answer is prescribed. `answer_contains` and `answer_omits` check case-insensitive literal substrings across all assistant replies. If truthful paraphrases are valid, use a semantic rubric instead. Add state/action checks and initial state through golden cases or a draft edit grounded in the known adapter contract. Objective checks of state/actions establish what happened inside the trusted sandbox; text checks do not establish a backend action. Without deterministic checks the objective outcome is ungraded, even if a model rubric estimate says pass. The model assessment is a separate evidence layer: require actual event references for pass/fail, return unknown when the trace is insufficient, and distinguish assessment failure from target failure. Valid reference IDs do not prove that the cited event supports the interpretation. Human approval of a rubric is not calibration of the model judge; measure agreement with human labels before making reliability claims. Synthetic performance alone does not establish production performance.

Schema validation checks the simulator's message shape, not whether it faithfully followed its role. Audit actual transcripts against facts, persona, goal and behavior, including passing cases. Look for invented facts, premature stopping, role drift, or excessive help. The model's simulator-fidelity rubric can flag suspected failures but cannot establish semantic validity. If a human audit finds them, mark the affected evidence unreliable, correct the draft and rerun the agent under newly approved criteria. Use consented real-user traces to assess transfer; do not infer it from synthetic scores.

The nested builder/target/simulator Pi sessions disable discovered skills, extensions, inherited context and built-in filesystem/shell tools. This capability boundary protects the nested model-facing evaluator. The outer Pi conversation is the trusted operator and may retain its usual authorized tools. The local human owner can inspect all artifacts; local file permissions are not an untrusted-code sandbox. Do not feed consumed control traces into another optimizer and still describe that suite as independent.

## Scenario and grading rules

- Start with ordinary successful requests. Add incomplete information, contradictory requests, changed intent, irrelevant information, unsupported actions, transient tool errors, and preservation of unrelated state where the source requirements justify them. Each family tests a distinct failure mechanism; wording variants remain in the same family.
- Assign synthetic fixture values explicitly. The simulator receives its goal, facts, behavior and actual conversation; expected checks are excluded from its context. Instruct it to answer from those facts, stop naturally, resist role-change requests, and avoid assigning scores or inventing tool results. Assigned single-request or no-further-request behavior takes priority over achieving the goal: an honest failure can end the dialogue. Do not repeatedly demand another attempt to force success, or invent/repeat a clarification or staged revision absent from the assigned behavior. Verify this behavior by auditing transcripts. Natural conversation completion and objective task success are separate outcomes. The simulator may end the conversation like a real user when it is blocked or refused; treat such endings as valid user behavior, not simulator failure, and expect persona traits at ordinary intensity rather than caricature.
- Every newly generated card declares user.maxFollowUps. Zero allows only the opening request and its target response; one permits one reactive user follow-up. Assign a larger value only for explicitly required interactions, ensuring enough turns for the intended clarification or staged request. The evaluator enforces this budget independently of the model's done flag. It bounds interaction length and prevents extra attempts; it never establishes task success or semantic fidelity. Older saved cards without this field retain their existing global turn limit.
- Simulator output uses explicit final-message semantics: done:true with a nonempty message delivers that final message, receives the target's response, then ends. done:true with an empty message stops immediately. A promised final clarification or changed request must be included in message even when done is true; it must not be discarded to end the conversation. done:false requires a nonempty message and may continue only within the declared follow-up budget.
- For missing-information cases, omit details from the opening but put the eventual exact record ID/value in user facts. If behavior promises to answer clarification, grade the eventual authorized action and final state across the whole dialogue. A no-update check is appropriate only if the user explicitly refuses to supply details or the entire task forbids changes. Do not require successful clarification using facts the simulated user does not possess.
- Keep internal failure schedules, retry counters, backend diagnoses and hidden record-existence facts out of the user projection. Those belong to the environment. Users may react to failures revealed by the agent, not predict future tool results. Even indirect goals such as succeeding "despite transient failures" reveal future errors before the user has observed them.
- Test changed intent across turns: opening contains the first request, facts contain both values, and behavior requires one different request after the first assistant response. Check the final state against the later request. Two conflicting values in the opening test single-message interpretation instead.
- Prefer final-state assertions for business actions. tool_called proves an attempt somewhere in the dialogue, not temporal order or success; tool_not_called forbids all attempts. fresh_read_before_update requires a successful read of the same record since its previous successful update; failed retries may reuse that read. With no updates the order condition is not exercised, so pair it with a changed-state assertion or tool_count minimum. tool_count counts all attempts, including failed/rejected ones, over the whole dialogue; a maximum of three tests two retries only for a single intended operation. Descriptions must match the implemented predicate.
- Do not invent action-count limits absent from source rules. Additional reads should not fail a case unless the source limits them; prefer tool_called when only a necessary action minimum matters. Count descriptions cannot imply success or temporal ordering.
- Use answer_equals only for a prescribed complete final response. Preserve expected spaces and newlines; an earlier matching reply does not satisfy it. answer_contains searches all assistant replies without regard to case; answer_omits is its inverse and forbids wording that must never reach the user, such as staff-only instructions or internal system names the source itself forbids. Forbid only what a source forbids: a phrase invented by the card fails on harmless wording. Use literal checks for exact requested fixture values or source-mandated wording, not an invented failure phrase that rejects truthful synonyms. Do not invent magic phrases or coach the simulated user to demand them merely to create a passing check. Every expected state field must exist initially, and changes must be possible through the allowed writable fields. An unreachable scenario is invalid rather than an agent failure.
- Ground every business requirement in an exact source quotation and link each scenario to known requirement IDs. Missing or conflicting policy remains a question for the owner; generating more tests cannot resolve an unknown business decision. Human approval of generated scenarios makes their provisional nature visible but does not prove a judge is calibrated.
- Define subjective rubrics narrowly enough for a human to explain pass/fail from evidence. The implemented judge uses those rubrics but has not thereby been calibrated; label its estimates provisional and compare them with human labels. The evidence summary computes that comparison from recorded human verdicts; until a metric has sixty or more labeled pairs its rates are flagged as insufficient. Do not substitute a generic model score, model confidence, or answer keyword for correctness of an action.

## Optional comparison and evidence rules

The legacy automatic sandbox optimizer is a separate, explicitly selected `compare` workflow. External agents use repeat and comparison of completed `evaluate` runs. It can propose declarative instruction/tool-allowlist changes under an approved scope; it is not the default four-step evaluation. Never let the model approve a draft, silently change an existing agent, or deploy an exported configuration. Plain evaluation runs the supplied agent unchanged.

- Compare baseline and candidate on identical scenario/repetition keys, suite/check/simulator/environment settings and reset state. Changed criteria require regrading the baseline in a new experiment. Duplicate, missing, cancelled and invalid trials cannot be silently excluded to improve the reported score.
- Keep the prior best unless the development comparison is complete, has no regression, and fixes at least one failed trial. The application enforces this rule, evaluator ownership, bounded iteration, and one final control phase. A model's recommendation cannot override them.
- Report paired fixes, regressions and ties. Aggregate repeated trials within scenario families before estimating uncertainty, then weight families equally. The application counts declared family IDs; it does not verify that their mechanisms are independent. Audit overlapping mechanisms, such as retry handling and truthful outcome reporting tested by the same retry trajectory. Many paraphrases or new IDs for one mechanism do not become independent observations. A positive descriptive delta can coexist with insufficient evidence.
- Classify provider errors, malformed model output, invalid scenarios, simulator protocol errors, timeouts, budget stops and cancellation separately from valid task failures. Retain the trace and reason; do not retry invisibly until a favorable outcome appears.
- Save instructions, tool allowlist, source/suite fingerprints, model/provider settings, trial pairing, observed usage/cost, elapsed time, tool attempts/results and state. Unknown price/usage remains unknown. A usage budget is a bound on calls, not a guaranteed provider billing cap.
- The final result includes the original and selected AgentSpec, the hypothesis and development decision for each revision, control comparisons and representative failure/success traces. State exactly whether evidence is scripted, synthetic with a live model, or based on real-user data. Do not claim production improvement from simulation alone.

## Pilot evidence and scope

For the current PoC, inspect one existing local agent, prepare its callable entry point and start with five reviewed scenarios. Understand the user goal, known facts, private external state, possible clarifications, state transitions and completion criteria. Read available files before asking for missing details. A golden set and de-identified production dialogues can strengthen a later pilot; their absence does not block the local PoC. Do not invent pilot data or assume an adapter exists before inspecting it.

Build a mixed evidence set: preserve reviewed golden and production-derived cases with their provenance, then add synthetic cases to address specific gaps. A fully synthetic run remains a synthetic run. Define capability cases for current failures and regression cases for behavior that must not worsen; both inform candidate selection. Keep held-out evaluation separate from the material used to make changes.

Before claiming the reactive simulator adds value, compare it with a static expanded test set and scripted multi-turn scenarios on the same agent version, reset states, criteria and comparable budgets. Measure confirmed new failure mechanisms, useful trajectory coverage, disagreement with real/human-reviewed outcomes, cost and time. More dialogues alone is not additional value. Trace-audit simulator failures such as fabricated knowledge, excessive help, goal drift, premature completion and loops. settings.userModes runs that three-way comparison on the same cards, and the evidence summary lists the failing checks only the reactive mode exposed. Production logs enter as dialogues in the documented JSON format; there is no connector to logging platforms.

Prompt-only improvement is a proposed first pilot scope, to isolate cause and effect. Agree the editable components before applying changes; AgentSpec supports instructions and the registered-tool allowlist and does not enforce prompt-only changes. Do not promise such enforcement without adding it. The default native workflow requires human draft and result review; approval to evaluate is not approval to change or deploy the agent. Running the built-in example supplies no real pilot data; the module target example is a reference adapter, not the owner's agent.

This protocol is self-contained. Nested model sessions have no browser, search-engine or filesystem tools; repository inspection uses the outer Pi session's file and shell tools. No external article retrieval is needed.
